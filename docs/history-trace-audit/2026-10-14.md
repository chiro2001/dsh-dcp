# 历史 session trace 对照设计审计（2026-10-14）

结论：日志与 checkpoint 提交架构应保留；默认保留窗口、混合消息 cleanup 与子代理
来源保护需要调整。此前官方模型三轮回归证明了合成夹具中的提交/清理/召回路径，
历史工作负载暴露了这些夹具没有覆盖的长 turn 和 reasoning 形态。

本轮只读分析，没有模型调用；原始用户消息、推理、工具参数和结果未输出或落盘。
只归档匿名 hash、计数、长度和结构类别。本轮未修改生产压缩代码。

## 数据与口径

- 本机历史中，排除既有 TUI 前端插件相关项目后，有 817 个物理 trace、816 个逻辑
  session ID。实际 header 为 v0 的 502 份、v3 的 315 份，创建日期覆盖
  2026-08-13 至 2026-09-26；当前安装的 dsh `0.2.0-rc.2` 逻辑格式为 v4。
- 通用分析按版本各抽 30 份，再按压缩文件大小/创建时间分层，并纳入每版本最大文件。
  60 个样本不同 ID，全部完整且 seq 连续。此分层样本不能直接当成全库随机抽样比例。
- DCP 定向分析另外读取本项目对应的 25 个会话，以及每版本 8 个跨项目探针，共
  41 个不同会话；与通用样本部分重叠，两组不能相加当成独立样本。
- 成本组成只统计最终消息的正文、reasoning、工具参数及工具结果正文；不重复统计
  `assistant/chunk`、`data.stream` 或 JSON 包装。单位为 Unicode 字符，**不是 API
  tokens、账单或最终重放后上下文窗口**。原始日志大小也不代表请求大小。
- 原始 trace 的宿主版本和 DCP build 不等价；没有可靠持久化的插件 build 版本。
  下列判断是历史工作负载与当前代码的对照，不能说 rc.9 已在这些旧会话部署并失败。

证据：[通用聚合](2026-10-14/generic-summary.json)、
[DCP 聚合](2026-10-14/dcp-history.json)、[合成结构复现](2026-10-14/static-probes.json)。
只读分析工具为 [audit-history-traces.ts](../../scripts/audit-history-traces.ts)。

## 1. turn 不是合适的唯一资源保护单位

| 样本组           | 会话数 | turn 数 | 每 turn step 中位数 | p90 | 最大值 |
| ---------------- | -----: | ------: | ------------------: | --: | -----: |
| 主会话，全部样本 |     17 |     552 |                   5 |  16 |    255 |
| 子会话，全部样本 |     43 |      66 |                  79 | 223 |    463 |
| 子会话，v3 子集  |     25 |      35 |                 120 | 312 |    463 |

v3 子会话的 35 个 turn 中，22 个超过 100 steps（62.9%）。主会话多数 turn 较短，
也存在 255-step 的长轮次。因此现有保留窗口对短轮次有合理性，但不能覆盖长期自主执行。

当前 `retainRecentTurns=2` 会保护当前及前一个 turn；即使当前 turn 已完成上百个
step，这些前缀仍会被 `RECENT_RANGE` 拒绝。只切换 `references.granularity=step`
不会改变这一规则。离线复现还确认：一个 14-step 单 turn 可以收到 fallback nudge，
同一会话的闭合早期范围却被保留窗口拒绝。提醒没有先确认可用候选。

建议：设计当前 turn 的闭合前缀压缩，保护初始用户目标、后续有效 steering、近期
step/token 尾部、开放工具对、当前请求与 system/developer；再按需提供边界。
这属于需要新增安全契约和测试的设计变更，不能只把整轮保护开关关闭。

## 2. pure-only cleanup 与历史模型输出不匹配

41 个定向样本中，6 个旧会话实际执行了 `compress`，共 39 个 call ID；39 个都有
对应结果。另 3 个只有正文中的标记/指针，不算插件执行。

按 call ID 去重并取原始 append 作者后，39/39 都含 reasoning，4/39 还含普通文本，
纯 tool-call 为 0。原日志有 55 条相关 assistant 事件，其中存在旧 replacement 副本，
不能把 55 当成独立调用次数。

当前 `step-cleanup.ts` 只接受纯 compress tool-call 消息。这批作者形态若进入当前
条件检查，会全部被第一层 shape gate 排除；原生结果是否已消费、区间是否闭合及
清理是否省 token 都还没有机会检查。由于旧日志的 surface 规则不同，本轮没有把它
换算成“当前部署 cleanup 成功率”。

现有官方模型回归采用 thinking disabled，部分夹具还要求工具调用不附带正文。
这些通过结果不能替代 thinking 或自然解释文本场景。应设计能保留正文/reasoning 含义、
同时归档重复 summary 的持久流程，并加入 thinking enabled 的真实回归。

同时应测量完整压缩周期的后续请求成本：范围替换节省、摘要调用参数、工具结果、
保护附录、cleanup 提示都要纳入，而不仅检查单个 checkpoint 比原范围小。

## 3. 来源保护存在可复现的字段匹配遗漏

旧压缩范围中可识别 104 条不同子代理来源消息：96 条 `kind=subagent-settled`、
`form=notice`，8 条 `kind=subagent-report`。其 form 都没有命中当前配置的
`protectedSources`；旧 checkpoint 没有逐字包含这些消息。**这不证明摘要丢失了事实。**

当前安装的 dsh-subagent 仍使用 `kind=subagent-settled, form=notice`。配置写的是
`subagent-settled`，但 `collectProtectedAppendix` 只匹配 `source.form`。合成消息
复现结果为没有保护附录。因此这是确定的来源匹配问题，应先修正 kind/form 语义，
并保留必要的旧来源识别；也应明确新版 `agent-message` 是否需要按用途保护。

## 4. PTC 与嵌套暂缺历史验收证据

- 此次 41 个定向样本没有 `run_code`、PTC/code dispatch，不能说 PTC 是历史高频失败原因。
  当前安装版本的离线结构复现表明：PTC-only 隐藏模型直调 `compress`，插件又拒绝
  `exec.parent`；`/dcp compress` 只调度 followup，不会改变工具呈现模式。
  因此需要单独定义 PTC 下可用的压缩入口，或明确检测、提示受限模式。
- 识别出 30 条结构有效的旧 v1 checkpoint，均与对应 compaction summary 文本相同，
  能覆盖 17 个调用；其余 22 个调用没有匹配 checkpoint，记为 unknown，不判失败。
  旧结果格式未被审计解析器识别为当前状态文本，不计算 success/partial/rejected 比例。
- 30 条 checkpoint 没有已提交的嵌套附录，无法从本轮数据评价嵌套增长。当前原样携带
  旧块有保真价值，但其长期空间收益需要单独实验，不能只凭嵌套召回用例通过作结论。
- 宿主记录的旧 `shadowedTokenCount` 与当前估算器输出不是同一测量体系，本报告不把
  两者相减作为当前设计的实际净省或 API 用量。

## 处置顺序

1. 修来源保护字段匹配，并补真实 producer 形态的回归。
2. 优先设计并验收长 turn 的闭合前缀压缩；让 nudge 有可用候选再触发。
3. 为 reasoning/text 混合作者设计清理及完整周期计量，使用官方 DeepSeek thinking
   模式复测合成的真实历史结构；不向外部模型发送这些私有历史原文。
4. 定义 PTC 与子会话的支持边界；随后评估嵌套摘要预算。

继续保留：标准日志事务、模型请求与派生视图一致、工具配对、硬保护、原始日志可恢复、
先消费原生结果再 cleanup、失败不误报提交。这些规则仍是适配 dsh 的正确基础。
